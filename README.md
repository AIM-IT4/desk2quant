# Desk2Quant

Desk2Quant is a quantitative-finance learning and mentorship platform with interactive resources, booking workflows and digital-product delivery.

## Features

- Mentorship booking with dynamic time slots and conflict detection
- Digital-resource catalogue and purchase flow
- Free quantitative-finance learning resources
- Razorpay payment integration
- Brevo transactional-email integration
- Supabase-backed bookings, products and session data
- Administrative workflows for bookings, rescheduling and analytics
- Responsive browser-based interface

## Technology

- Frontend: HTML5, CSS3 and vanilla JavaScript
- Database and storage: Supabase/PostgreSQL
- Payments: Razorpay
- Transactional email: Brevo
- Hosting: Vercel

## Repository structure

The application is served from the repository root (`outputDirectory: "."` in `vercel.json`), so anything in the root is web-reachable unless it is listed in `.vercelignore` or sealed by a redirect in `vercel.json`. Keep that in mind before adding files.

```text
.
├── *.html, *.css, *.js     Hand-written site pages and their scripts (index, product, my-access,
│                           my-bookings, mentors, blog, faq, admin, salary-explorer, ...)
├── products/               GENERATED product pages (one per Supabase product) - rebuilt on deploy
├── blog/                   GENERATED article pages from the Supabase `blogs` table - rebuilt on deploy
├── guides/                 GENERATED interview guides from scripts/seo-guides-data.js - rebuilt on deploy
├── sitemap.xml             GENERATED sitemap - rebuilt on deploy
├── api/                    Vercel serverless functions (payments, webhook, access links, emails, reminders)
├── lib/                    Shared server code imported by api/ (pricing, secure downloads, email branding, ...)
├── scripts/                Build pipeline (build-seo.js, seo-*.js) and operator tools (db, drive, vercel, linkedin, ...)
├── test/                   node:test suites (`npm test`)
├── supabase/migrations/    Database schema and RLS migrations (source of truth for the schema)
├── assets/                 Images, covers, downloads and per-product sample PDFs
├── content/                Article source copy kept for editing (not deployed)
├── docs/                   Internal notes (blocked from web access by vercel.json redirects)
├── email-templates/        Transactional email HTML
├── .github/workflows/      CI and scheduled jobs
├── ARCHITECTURE.md         System design
├── DATABASE_GUIDE.md       Tables and policies
├── PROJECT_GUIDE.md        Contributor notes
└── SECURITY.md             Security model
```

Things that look unused but are not:

- `assets/samples/<product-id>_sample.pdf` is built at runtime by `product.html` for the "Peek Inside" button. Do not delete by name search.
- `google*.html` and the long hex `.txt` files are search-engine ownership and IndexNow key files.
- `index-test.html`, `product-test.html` and `styles-test.css` are the test catalogue used by `script.js` (not served in production).
- Files under `products/`, `blog/`, `guides/` are regenerated by the build, so edit their sources instead (see below).

## Local setup

```bash
git clone https://github.com/AIM-IT4/desk2quant.git
cd desk2quant
npm install
npm test
python -m http.server 8000
```

Then open `http://localhost:8000` in a browser. Generated pages (`products/`, `blog/`, `guides/`) are committed snapshots; production regenerates them on deploy.

## Build and SEO product pages

Vercel runs `npm run build` (`generate-config.js` then `scripts/build-seo.js`) on every deployment. It needs Supabase access, so it cannot run in a sandbox without network access to the project.

- **Product pages** under `products/` are regenerated from the Supabase `products` table, together with the product hub and `sitemap.xml`. After a product is added or edited in Supabase (name, price, description), a deployment is required before its canonical `/products/<slug>.html` page reflects it.
- **Articles** under `blog/` come from the Supabase `blogs` table (`title`, `slug`, `excerpt`, `content`, `cover_image_url`, `is_published`). Publishing a new row and deploying creates `/blog/<slug>.html`.
- **Guides** under `guides/` come from `scripts/seo-guides-data.js`.
- **Hand-tuned titles and descriptions**: `scripts/seo-overrides.js` overrides the generated `<title>` and meta description for a given slug (keep titles within 60 characters including the brand suffix, descriptions within 158).

## Commands

| Command | Purpose |
|---|---|
| `npm test` | Run all `node:test` suites in `test/` |
| `npm run test:seo` | SEO routing, metadata, build-safety and homepage tests |
| `npm run build` | Generate product, blog and guide pages and the sitemap (needs Supabase) |
| `npm run check:seo` | Audit built SEO output |
| `npm run check:search-console` / `test:search-console` | Search Console report and its self-test |
| `npm run indexnow` / `indexnow:dry-run` | Submit changed URLs to IndexNow |
| `npm run db` / `drive` / `vercel` / `linkedin` | Operator tools for Supabase, Google Drive, Vercel and LinkedIn |

Other files in `scripts/` are standalone operator utilities (carousel builders, Reddit and LinkedIn helpers, Drive-permission audits, email previews). Run them manually; nothing in the deployed site imports them.

## Configuration

### Supabase

1. Create a Supabase project.
2. Apply the repository's SQL migrations or setup scripts.
3. Configure the Supabase project URL and public client key using the project's supported configuration mechanism.
4. Keep service-role keys and other privileged credentials on the server side only.

### Razorpay

1. Create Razorpay API credentials.
2. Store secret values in server-side or deployment environment variables.
3. Configure the payment webhook for the required payment events.
4. Verify webhook signatures before updating bookings or fulfilling digital products.

### Brevo

Configure transactional-email credentials through server-side environment variables or protected serverless functions. Do not expose private API keys in browser JavaScript.

## Security notes

- The Supabase anonymous key may be used client-side only with appropriate Row Level Security policies.
- Administrative access should use Supabase Auth or another server-verified authentication mechanism.
- Payment and email secrets must never be committed to the repository or embedded in client-side code.
- Production deployments should validate payment webhooks and authorization on every privileged operation.
